# Plan 13, T0: what OFFBEAT does with a TRISO particle

Done 2026-10-15 for [plan 13](../plans/13-triso-particle.md), milestone T0, through the real solver (feed-solver distro, user `feed`, OFFBEAT `80e84450`, OpenFOAM 9). **Gate met: a thermal-only particle runs in OFFBEAT, and its temperatures agree with the closed form of a layered sphere to 0.1 K of a 48 K rise (0.2 %), so the plan does not stop for the user's decision on an independent-only particle.** The probe is a set of throw-away scripts that copy OFFBEAT's own tutorial case `generic_TRISO_1D` to `~/spike/t0/<name>` and edit the copy (kept as `.txt` in [triso-probe/](triso-probe/)); OFFBEAT's source tree and FEED's source were not changed. Run them as `wsl -d feed-solver -u feed -- bash <script>` (as root the OpenFOAM build is not on the path: `offbeat` gives "not found"/"permission denied"). OFFBEAT is GPL-3.0; no OFFBEAT file is kept in FEED (the scripts only name its paths).

Particle of the probe (the tutorial's, micrometres): kernel radius 251, buffer 95, IPyC 41, SiC 35, OPyC 40 (outer radius 462). Heat: 3e9 W/m3 in the kernel only (0.1987 W per particle). Constant conductivities (W/m/K): buffer 0.5, IPyC 4, SiC 13.9, OPyC 4; the kernel 3 (the tutorial's UO2 correlation is replaced by a constant for the closed-form comparison; with the correlation the run also works). Mesh: 12 cells in the kernel, buffer, IPyC and OPyC, 16 in the SiC, unless stated.

## Answers

|---|---|---|
| **Does the shipped tutorial run as it is?** | `run-asis.sh.txt`: its `Allrun` steps by hand | **Yes, up to its last step.** 1780 steps to the end time 5e7 s in **17.6 s** (mesh 0.2 s). It then aborts (exit 134): "Supplied value 5e+07 is out of bounds (0 ... 5e+07)" in the heat-source table (`timeDependentVhgr::nextTimeMarker`), because the table's last point (5e7) equals the end time. The same OFFBEAT behaviour FEED already handles for boundary tables (plan 11: a point is appended beyond the end time). The last time written is 4.93e7 s (every 50 steps). |
| **Can the mechanics be switched off?** | `mechanicsSolver fromLatestTime`, `fgr none`, a heat table to 1e9 s | **Yes.** `fromLatestTime` is the documented "no mechanics" choice. The run completes (exit 139 after complete output, the accepted pattern), two time steps to 20 s, no `D` file needed beyond the tutorial's `0/DD`. The burnup, fast-flux and creep models stay on in the tutorial's dictionary and only add time-step limits (31132 s from the burnup model); whether they can be removed is **not tested** (left for T3). |
| **Is a gas model needed for the buffer-IPyC gap?** | `0/T`: `trisoGap` (needs `gapGas`) against `resistiveGap` with a fixed `alpha`, the BC FEED writes for the pin | **Both run thermal-only.** (i) `trisoGap` with `gapGas TRISO` and `fgr none` runs; with the shipped zero-width gap its conductance (read from `trisoGapFvPatchScalarField.C`: `hGas = k_gas / (gap + roughness + jump distance)`, plus radiation, plus contact) gave a gap drop of about 0.5 K. (ii) **`resistiveGap` with a stated `alpha` runs with `gapGas none`**: the same BC and the same input (a gap conductance, W/m2/K) FEED already has for the pin. With alpha 1.5e5 the gap drop is **0.881 K against 0.8806 K** from the closed form (q''/h at the gap radius). A non-zero gap width in the mesh was **not** run (the particle keeps a zero-width gap and a conductance, like the pin). |
| **The mesh (a wedge for a sphere)** | the point formulas of `sphereMaker.py`, the mesh volumes and the outer-face area | The mesh is a **2 degree double wedge**; its vertices satisfy x^2+y^2+z^2 = r^2 exactly, so **the radius of a cell is the length of its cell-centre vector**. The cell volumes are the same fraction of the sphere's in every layer (9.6894e-5; the manual states 9.6963e-5, 0.07 % higher), and the outer and gap faces are 9.6923e-5 of 4 pi r^2 at every radius. Heat per volume and flux per area therefore scale together to within f_v/f_a = 0.9997: **no radius-dependent error, a 0.03 % flux factor** (it explains the 0.011 K wall offset below). The log prints "angular fraction 0.00555556" (= 2/360), the pin's convention, not the particle's fraction. |
| **Kernel temperature against the closed form** | `analyze.py.txt`: shells with constant k, kernel parabola q R^2/(6k), gap q''/h, fixed wall 1298 K | **Agrees.** Largest cell deviation by mesh (cells per layer ×0.5, ×1, ×2, ×4): kernel **0.218, 0.050, 0.027, 0.010 K**, IPyC 0.096 to 0.020 K, SiC 0.045 to 0.011 K, OPyC 0.008 K, **buffer 0.19, 0.113, 0.089, 0.076 K** (does not go to zero). The whole rise (kernel centre above the wall) is 48.2 K. The buffer's deviation is -0.046 K next to the gap, growing to -0.074 K at the kernel side (a 4 % shortfall against the 0.88 K gap drop at the gap), and is **unexplained**; T3 sets the tolerance from the finest mesh (0.3 K or 0.5 % of the rise), not from this probe. |
| **A convective outside** | `0/T` `outer`: `convectiveHTC`, T0 900 K, h 2000 W/m2/K | **Works, but the run must be long enough.** A 20 s run (two steps: 1 s, then 19 s) was **not steady** (wall 937.31 K, 0.27 K above the closed form 937.043 K, the same absolute offset at h = 200; 0.007 K at h = 20000). Runs of 200, 2000 and 1e5 s give 937.058, 937.034, 937.032 K: **converged to 0.011 K below the closed form** (the 0.03 % area factor above). So the end time of a steady particle must come from a time scale, as FEED's `steadyEndTime` does for the pin (to be written for the sphere in T2); a fixed wall (the tutorial's `fixedValue`) was steady in 20 s. |
| **Cost per particle** | wall clock of `offbeat` | **0.07 to 0.1 s** for 64 to 256 cells and two steps, plus 0.1 s for the mesh. A population of 1000 sampled particles through OFFBEAT is a few minutes in a serial loop: possible for SEED, though FEED's independent solver stays the choice for thousands. The tutorial's 600 day irradiation with the fission-gas and gap models is 18 s. |
| **What the reader must read** | the written time directory | `T` at cell centres, the cell-zone names (`Kernel`, `Buffer`, `IPyC`, `SiC`, `OPyC` in `constant/polyMesh/cellZones`) to put each cell in its layer, `C` (cell centres, from `postProcess -func writeCellCentres`) for the radius, the patch values of `bufferOuter`, `ipycInner` and `outer` in `T`'s boundary field. The time directory of a 20 s run is named `2e+01` (OpenFOAM's format), as in the pin cases. |
| **`sphereMaker.py`** | read, run on a copy | It writes `./blockMeshDict`; the case reads **`system/blockMeshDict`** (the first mesh study used the stale one: copy it over). The `Kernel` layer without a `Buffer` is not allowed. FEED will write its own mesh from the vertex formulas above; the script is not copied. |

## What this changes in the plan

- **D4 (the gap) is settled:** the gap is an **input conductance** (W/m2/K at the buffer outer radius), through the same `resistiveGap` as the pin, with **no gas model, no fission-gas code and no `gapGas`**. FEED may offer a helper that turns a gas conductivity and a width into that number (the OFFBEAT formula above), shown as a derived value.
- **The steady end time** of a particle is a time scale of the sphere (T2), not a fixed number; a fixed wall hides this.
- **Heat tables** need a point beyond the end time (as the boundary tables of plan 11).
- **A population through OFFBEAT is cheap** (0.1 s per particle), so the SEED batch is not limited to a handful: a few hundred sampled particles are realistic; the plan keeps FEED's independent solver as the primary population engine and uses OFFBEAT for a representative subset plus any check the user wants.
- **OpenMC Studio's own example** (`examples/triso-particle` in the Studio repo, checked 2026-10-15 at `321ce38`) is a five-layer particle: UCO kernel radius 250 um, buffer 100, IPyC 40, SiC 35, OPyC 35 um (outer radius 460 um), densities 10.5, 1.0, 1.9, 3.2, 1.9 g/cm3, **illustrative values** (its README says so), with a fixed-source tally and no packing. FEED's generic example uses the same dimensions so the two apps describe one particle; the conductivities and the heat are FEED's own (Studio's file carries none). Studio's TODO section 2c plans a TRISO package (a packed compact or pebble with `pack_spheres`) "when TRISO users exist", which is where a packing fraction would come from on its side.
- **Not probed (left to T3 or later):** a transient with a real heat table (a pulse), a non-zero gap width in the mesh, a temperature-dependent buffer or PyC conductivity (the tutorial's PyC correlations are mechanics-related and not switched on here), the UO2 correlation checked against an independent evaluation (the run works with it in the shipped `trisoGap` case; not compared with a closed form), and removal of the burnup, fast-flux and creep models.
